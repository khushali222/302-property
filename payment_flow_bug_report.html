🔴 Critical Bugs

Critical
BUG #1 — storePaymentfornormal hardcodes 'response': "SUCCESS" — scheduled payments saved as already paid
Admin Staff  · lib/repository/payment/payment_service.dart (line 706) · lib/StaffModule/repository/payment/payment_service.dart (line 690)
click to expand ▾

When a Check / Cash / Money Order payment is scheduled for a future date, the code calls storePaymentfornormal(responseText: "PENDING"). However, inside storePaymentfornormal, the body ignores the passed responseText parameter and hardcodes 'response': "SUCCESS".

// admin lib/repository/payment/payment_service.dart ~line 695 Future<Map<String, dynamic>> storePaymentfornormal({ ... required String responseText, // caller passes "PENDING" ... }) async { final response = await http.post( Uri.parse(baseUrl), ... body: jsonEncode(<String, dynamic>{ ... 'response': "SUCCESS", // ❌ BUG: hardcoded — responseText param is ignored! // 'response': responseText, // ✅ FIX: use the passed parameter }), ); }
🔴 Impact: A Check/Cash payment scheduled for next month is recorded in the DB as "SUCCESS" (already paid) the moment the admin creates it. This corrupts the payment ledger, falsely reduces the tenant's outstanding balance, and means the cron-job scheduler may never fire because it only processes PENDING records.
✅ Fix: Change 'response': "SUCCESS" → 'response': responseText in storePaymentfornormal in both Admin and Staff payment_service.dart files.
Critical
BUG #2 — Tenant makePaymentfornormal missing 'await' — scheduled payment silently dropped on failure
Tenant  · lib/TenantsModule/screen/financial/payment/payment_service.dart (line 556)

In the tenant module, when a normal (check/cash) payment is scheduled for a future date, storePaymentfornormal() is called without await and without a try/catch. The function fires-and-forgets. If the API call fails (network error, server error), the tenant sees "Payment Successfully" but nothing is stored.

// lib/TenantsModule/screen/financial/payment/payment_service.dart ~line 554 } else { try { storePaymentfornormal( // ❌ Missing await! Fire and forget. await storePaymentfornormal( // ✅ FIX: add await companyName: company_name, ... responseText: "PENDING", ... ); return "Payment Successfully"; // returned even if storePayment failed } catch (e) { throw Exception(e); } }
🔴 Impact: A tenant schedules a future payment. The server call fails silently. The tenant app shows "Payment Successfully" but no record exists in the DB. The tenant thinks they've paid; the admin sees nothing.
✅ Fix: Add await before storePaymentfornormal() so exceptions propagate to the catch block and the error is shown to the user.
Critical
BUG #3 — Edit Payment (Admin/Staff) card charges always stored with surcharge "0"
Admin Staff  · lib/repository/payment/Edit_payment.dart (line 165) · lib/StaffModule/repository/payment/Edit_payment.dart
click to expand ▾

In the Edit Payment service, makePaymentforcard hardcodes surcharge: "0" when calling storePayment(), regardless of the actual surcharge amount passed in. The surcharge parameter is even commented out from the function signature.

// lib/repository/payment/Edit_payment.dart Future<String> makePaymentforcard({ required String adminId, // required String surcharge, // ❌ commented out! required String amount, ... }) async { await storePayment( ... totalAmount: amount, surcharge: "0", // ❌ hardcoded — always 0 regardless of actual surcharge // surcharge: surcharge, // ✅ FIX ... ); }
🔴 Impact: When editing a card payment that had a surcharge (e.g., 3%), the edited record saves surcharge=0. The stored total_amount (which = amount − surcharge) will also be inflated since surcharge "0" is subtracted, resulting in a wrong total. Financial reports will be inaccurate.
✅ Fix: Uncomment surcharge in the function parameters and pass the actual surcharge value to storePayment().
Critical
BUG #4 — Edit Payment card NMI charge is fully commented out — editing an immediate card payment never charges the card
Admin Staff  · lib/repository/payment/Edit_payment.dart (lines 73–176)

The entire card-charge block in makePaymentforcard inside Edit_payment.dart is commented out. Regardless of whether future_Date is true or false, the code always skips the NMI call and goes directly to storePayment() with responseText: "PENDING". The future_Date parameter is accepted but never used.

// lib/repository/payment/Edit_payment.dart ~lines 73–176 Future<String> makePaymentforcard({ ... required bool future_Date, // accepted but NEVER checked below ... }) async { // if (future_Date == false) { // ❌ entire block commented out // final String baseUrl = '/api/nmipayment/sale'; // ...NMI charge logic... // } else { try { await storePayment( ... responseText: "PENDING", // ❌ always PENDING, never charged ... ); return "Payment Updated Successfully"; } catch (e) { throw Exception(e); } // } }
🔴 Impact: An admin edits a pending card payment and sets it to "today" (immediate). They expect the card to be charged now. Instead, the payment is just re-stored as PENDING — the card is never charged. The tenant keeps being billed without the payment being processed.
✅ Fix (if intentional): If edit is only supposed to update metadata (not re-charge), add a comment and UI indicator explaining this. Fix (if unintentional): Uncomment the NMI card charge block and restore the if (future_Date == false) branching logic.
Critical
BUG #5 — Tenant storePayment sends full amount including surcharge (does not subtract surcharge)
Tenant  · lib/TenantsModule/screen/financial/payment/payment_service.dart (line ~215)
click to expand ▾

In the tenant module, storePayment() sends total_amount: double.parse(totalAmount) — the full amount including surcharge. Admin and Staff both subtract surcharge from total_amount before sending to the DB. This means tenant payment records show a higher total than actual rent paid.

// Tenant: lib/TenantsModule/screen/financial/payment/payment_service.dart ~line 215 'total_amount': double.parse(totalAmount), // ❌ includes surcharge // Admin: lib/repository/payment/payment_service.dart ~line 229 'total_amount': (double.parse(totalAmount) - double.parse(surcharge)), // ✅ correct // Staff: lib/StaffModule/repository/payment/payment_service.dart ~line 231 'total_amount': (double.parse(totalAmount) - double.parse(surcharge)), // ✅ correct
🔴 Impact: Tenant payment records in DB have total_amount that includes the surcharge fee. This inflates "amount paid" in reports, ledgers, and outstanding balance calculations for tenant-initiated payments. Admin and Staff records are correct but Tenant records are wrong.
✅ Fix: Change to 'total_amount': double.parse(totalAmount) - double.parse(surcharge) in tenant's storePayment().

🟡 Medium Bugs

Medium
BUG #6 — Check/Cash/Money Order payments routed through NMI ACH endpoint and stored as paymentType "ACH"
Admin Staff Tenant  · payment_service.dart → makePaymentfornormal (all modules)
click to expand ▾

When a Check, Cash, or Money Order payment is made for an immediate date, it is routed through /api/nmipayment/ACH_sale (NMI's ACH bank transfer endpoint). These are physical payment methods that should NOT go through NMI at all. Additionally, the follow-up store call uses paymentType: "ACH" instead of "Check" / "Cash".

// lib/repository/payment/payment_service.dart ~line 562 (Admin) Future<String> makePaymentfornormal(...) async { if (future_Date == false) { final String baseUrl = '$Api_url/api/nmipayment/ACH_sale'; // ❌ wrong endpoint for physical payment ... final response = await http.post(Uri.parse(baseUrl), ...); if (jsonData["statusCode"] == 100) { await storePaymentAch( ... paymentType: "ACH", // ❌ stored as ACH — should be "Check"/"Cash" ); } } }
🟡 Impact: Payment reports will show Check/Cash payments as "ACH" type. If NMI rejects the request (no bank details provided), the payment fails even though it shouldn't need NMI at all. This is a logical routing error.
✅ Fix: Check/Cash/Money Order payments should skip NMI and go directly to storePaymentfornormal() with the correct payment_method type. The NMI call should only be for Card and ACH bank transfers.
Medium
BUG #7 — Tenant makePaymentfornormal: 'entry' (charges) not included in NMI payload
Tenant  · lib/TenantsModule/screen/financial/payment/payment_service.dart (lines ~487–504)
click to expand ▾

For Card and ACH tenant payments, the entry array (charge breakdown) is included in the NMI payload. But for the normal/check payment flow, the paymentDetails map is built without including 'entry'. The backend NMI handler likely uses entries to post charges — omitting them could mean charges are not applied.

// Tenant makePaymentfornormal — missing entries Map<String, dynamic> paymentDetails = { 'admin_id': adminId, 'amount': amount, 'tenantId': tenantId, 'date': date, 'lease_id': leaseid, // ❌ 'entry': entries — missing! Card and ACH both include this }; // Tenant makePaymentforcard — has entries ✅ 'entry': entries.map((e) => {...}).toList(),
🟡 Impact: If the backend uses entry to apply ledger charges, normal tenant payments may not correctly allocate the payment to rent, fees, etc.
✅ Fix: Add 'entry': entries.map((e) => {...}).toList() to the paymentDetails map in makePaymentfornormal for the tenant module.
Medium
BUG #8 — Staff storePayment: staff_id used in auth header but adminId used in request body
Staff  · lib/StaffModule/repository/payment/payment_service.dart (storePayment / storePaymentAch methods)
click to expand ▾

In the Staff module, the HTTP request to store a scheduled payment sends staff_id in the authorization header (for identity) but sends adminid (from prefs) in the body as admin_id. This mismatch can cause the backend to reject the request if it cross-validates the header identity against the body.

// lib/StaffModule/repository/payment/payment_service.dart storePayment() String? adminid = prefs.getString("adminId"); String? id = prefs.getString("staff_id"); final response = await http.post( ... headers: { "authorization": "CRM $token", "id": "CRM $id", // ❌ staff_id in header }, body: jsonEncode({ 'admin_id': adminid, // ❌ adminId in body — different from header }), );
🟡 Impact: If the backend uses the header ID for authorization/ownership and expects it to match the body's admin_id, scheduled staff payments may fail with 401/403 or be attributed to the wrong account.
✅ Fix: Clarify with the backend team which ID should be in the header. Ensure consistency — either both use staff_id or both use adminId as appropriate for the authorization model.
Medium

🚨 3 NEW CRITICAL BUGS CONFIRMED BY BACKEND CODE
BUG A — Admin & Staff storePayment() is REJECTED by backend (400 error every time)
Backend (Payment.js line 144-151): validates sum(entries) === total_amount.
Admin/Staff send total_amount = amount − surcharge = 0.92, but entries sum to 1.00.
Backend sees 1.00 ≠ 0.92 → returns HTTP 400: "Integrity check failed — entries sum does not equal total_amount."
Result: ALL Admin and Staff card/ACH payments to /api/payment/payment FAIL with 400. The only reason payments ever appear to work is if the frontend ignores the error response.
BUG B — Edit payment (PUT) will fail if original payment had a surcharge
Backend (Payment.js line 2836 PUT route): validates sum(newEntries) === originalPayment.total_amount (DB value, immutable).
Edit_payment.dart hardcodes surcharge: "0". So if original total was $1.08 (rent $1.00 + surcharge $0.08), mobile sends entries summing to $1.00 only → Backend: 1.00 ≠ 1.08 → HTTP 400.
Result: Editing any payment that originally had a surcharge is ALWAYS rejected.
BUG C — tenant_id (snake_case) missing from NMI paymentDetails → allow_card / allow_ach check BYPASSED 🔒
Backend (NMI-response.js line 238 /sale, line 300 /ACH_sale): reads paymentDetails?.tenant_id (snake_case) to check if allow_card / allow_ach is enabled for that tenant.
Mobile sends tenantId (camelCase) only — tenant_id (snake_case) is absent → the if (tenantId) block is never entered → the restriction check is silently skipped.
Result: A tenant with allow_card: false or allow_ach: false can bypass that restriction and pay from the mobile app. This is a security/business logic bypass.
Note: once inside processSale, the DB write correctly resolves tenant_id || tenantId — only the permission gate is broken.
